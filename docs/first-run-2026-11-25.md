## 2. How the check works (Beads' own state model, nothing custom)

For every delegation, one beads issue in the ledger workspace `~/workspace/delegation-ledger/` (prefix `del`, binary `~/workspace/tools/beads/bd`):

| Proof required | Beads mechanism (tool's own command) |
|---|---|
| (a) Claimed | `bd update <id> --claim` — atomic claim; sets assignee to the claiming actor, status → in_progress, starts a lease. Double-claim by another actor is refused by the tool (observed this run). |
| (b) Actively working | `bd heartbeat <id>` — the holder refreshes the lease; lease freshness IS the activity signal. No heartbeat = no proof of life, however confident the narrative. |
| (c) Not stopped | `bd stale` lists issues gone quiet; `bd reclaim` reverts stale-lease in_progress issues back to ready (dead-worker recovery) so another lane can claim them. An open issue never claimed past its deadline is STALLED by definition. |
| (d) Artifact landed | `bd close <id> --reason="<artifact>"` — the reason must cite the artifact (commit sha / file / URL), and the verifier reads that artifact back on origin BEFORE the close counts. Wrong-actor close is refused by the tool (observed this run). |
| (e) Historical claims true | Claimed-commit existence audit (Section 8): every landing claim already made in ACTIVITY / team-outbox / lane reports is re-verified against origin; a sha that does not resolve in the claimed repo = NOT LANDED, registered as a P0 beads bug (del-ioc). |

Verification cadence: the monitor loop and any delegator run `bd list` / `bd stale` / `bd reclaim` / `bd status` against the ledger and report the tool's output. A delegation with no beads issue does not exist; narrative status never overrides tool output.
